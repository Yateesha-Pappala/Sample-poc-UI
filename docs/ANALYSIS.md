## 1. Architecture as it actually is

| Aspect                                                              | Reality in the portal                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Modules                                                             | None. 100% standalone components, `inject()`, `input()`/`output()`, signals.                                                                                                                                                                                                                                                                              |
| Styling                                                             | **No component stylesheets at all.** Every component styles with Tailwind utilities + the shared `.sui-*` layer. The "design system" is 2 files: `src/styles/theme.css` (Tailwind import, `@theme` brand tokens, `.dark` custom variant, base resets) and `src/styles/components.css` (`.sui-*` component classes). Documented in `src/styles/README.md`. |
| Dark mode                                                           | Class-based (`.dark` on `<html>`), toggled by `core/theme.ts`. Variant defined in `theme.css` as `&:where(.dark, .dark *)`.                                                                                                                                                                                                                               |
| Layout model                                                        | `AppShell` (header + horizontal tab-nav + internally-scrolling `<main>`) wraps the authed area: Dashboard, Activity, Customers. Auth pages (Login, Registration, Register-verify) and POC pages (Details, Workspace) render **outside** the shell, each with their own `<app-auth-navbar>` or a slim back-link header.                                    |
| **No sidebar**                                                      | Primary nav is a horizontal tab bar in the header, with a slide-down mobile panel below `sm`. There is no vertical sidebar anywhere.                                                                                                                                                                                                                      |
| **No toast system**                                                 | Feedback = inline `role="alert"` / `role="status"` blocks + one global `<app-loading-overlay>` driven by an HTTP-request counter.                                                                                                                                                                                                                         |
| **No standalone Table / Tabs / Pagination / Breadcrumb components** | These exist only as inline markup (one real `<table>` in `customers`, tab bars re-implemented inline in `dashboard`, `activity`, `poc-form-modal`, a pagination footer inline in `customers`).                                                                                                                                                            |
| Data access                                                         | `ApiClient` wraps `HttpClient` and returns `{ data, loading, error }` **signal triples** (`ApiResult<T>`). Components hold `signal<ApiResult<T>                                                                                                                                                                                                           | null>`and derive`computed()`view state. Two HTTP interceptors:`loadingInterceptor`(counter) and`httpInterceptor` (bearer token + 401 refresh-and-retry). |
| Charts                                                              | One hand-built SVG line/area chart (`usage-trend-chart`) — no charting library.                                                                                                                                                                                                                                                                           |
| Guided tour                                                         | `core/tour/*` + `<app-tour-overlay>` — a fully generic spotlight/coach-mark system driven by a `TourStep[]`. Zero business coupling.                                                                                                                                                                                                                      |
| Branding                                                            | Sails "Agentic AI" wordmark + a 3-path inline SVG logo, duplicated in `app-shell` and `auth-navbar`. Brand palette hardcoded in `theme.css` (`--color-brand-700` navy `#064a70`, `--color-brand-accent` cyan `#00b9ff`, dark surfaces `#0f131e` / `#141a2e`). Favicon `public/sails logo fevvicon.jpg`.                                                   |

### Deviation from your proposed `styles/_variables.scss` structure

The portal has **no SCSS** — it's Tailwind v4, where tokens live in a CSS `@theme {}` block, not Sass maps. Per your constraint _"keep the same tooling unless there's a strong technical reason"_ and _"adapt to the architecture already used"_, the template keeps Tailwind v4 + `.sui-*`. The design-system-values requirement is met by `styles/theme.css` (tokens) + a new thin `styles/_branding.css` (`@theme` overrides a project edits) rather than `_variables.scss`.

## 4. `.sui-*` delivery — `git subtree` (per your choice)

The two CSS files + README must stay in lock-step across the portal and every POC. Plan:

1. **Now:** vendor `theme.css` / `components.css` / `README.md` into `poc-template/src/styles/` (done in the scaffold). `styles.css` header notes they're subtree-managed.
2. **When the shared repo exists** (`sails/sui-design`, created by `git subtree split --prefix=src/styles` from the portal): both repos wire it as
   ```
   git subtree add   --prefix src/styles <sui-design-remote> main --squash
   git subtree pull  --prefix src/styles <sui-design-remote> main --squash   # to update
   ```
3. `docs/DESIGN-LAYER.md` in the template documents this for POC owners; day-to-day they never touch `src/styles/` except `_branding.css`.

I can't create the remote repo — that step is yours. Everything else works with the vendored copy in the meantime.
